# SmartRoute-Bench

[English](README.md) · **한국어**

**LLM 스마트 라우팅 게이트웨이**를 위한 벤치마크입니다. 자동 모델 라우팅이
프런티어 모델을 고정해서 쓰는 것과 비슷한 품질을 훨씬 낮은 비용으로 실제로
달성하는지, 그리고 비용을 더 쓴 요청은 정말 그럴 필요가 있었는지를 측정합니다.

대부분의 LLM 벤치마크는 *모델*을 측정합니다. 이 벤치마크는 *라우터* — 요청마다
어떤 모델이 처리할지 결정하는 계층 — 를 측정합니다. 여러 비교 대상(예: 고정
프런티어 모델들 vs 스마트 라우팅 가상 모델)을 현실적인 혼합 워크로드에서
동일하게 실행하고 **비용·품질·지연·라우팅 행동**을 나란히 보고합니다. v2부터는
라우터를 **oracle**(각 과제를 통과하는 풀 안의 가장 싼 모델)과도 대조해,
과잉 상향(싼 모델로 충분한데 프런티어에 지불)과 과소 상향(실패하는 모델로 보냄)을
둘 다 드러냅니다.

## 두 개의 스위트, 두 개의 트랙

같은 구조의 과제 스위트를 두 벌 제공합니다. 여러분의 사용자 워크로드에 맞는
쪽으로 라우팅을 측정하세요:

- **`tasks/base/` — SmartRoute-Bench (영어).** 기본 스위트.
- **`tasks/k/` — K-SmartRoute-Bench (한국어).** 같은 과제를 한국어 실무 과제로
  재저작(한국어 비즈니스 문서·한↔영 번역·한국형 페르소나·한국어 지식 소스).
  `--tasks tasks/k`로 실행합니다.

각 스위트는 **253과제·22개 카테고리**이고, **따로 보고하며 절대 합산하지 않는**
두 트랙으로 나뉩니다:

- **Track A — 실무(158과제·직접 저작·헤드라인).** 고객이 게이트웨이로 실제로
  보내는 일: 코딩·디버깅·tool use·에이전틱 세션·비즈니스 문서·정보 추출·
  구조화 생성·지시 준수·안전 경계·되묻기. 한 원본(`tasks/_src/`)에서
  한·영을 함께 저작해 두 스위트가 따로 낡을 수 없고, 과제마다 `pair_id`로
  한/영 쌍이 묶여 있습니다.
- **Track B — 능력(95과제·공개 데이터셋 표본·보조).** 난이도 폭을 만들고
  글로벌 라우터 벤치와 수치를 비교할 수 있게 하는 짧은 객관식·수학·논리·
  장문 QA. **이 저장소는 행이 아니라 포인터만 담습니다**:
  `configs/track_b_manifest.json`·`track_b_lock.json`이 각 항목의 데이터셋·
  스플릿·인덱스·라이선스를 지정하고, `tools/fetch_track_b.py`가
  `tasks/*/capability/*.jsonl`을 로컬에 생성합니다(gitignore). RouterArena
  평가셋과 겹치는 항목은 표본 추출 단계에서 제외됩니다.

v1 스위트의 57과제는 현재 스위트 안에 **바이트 단위로 동일하게** 남아 있어
(`v1_category` 표식), 옛 스위트와 새 스위트의 실행을 그 교집합에서 비교할 수
있습니다 — 누가 하나라도 고치면 `tools/check_v1_continuity.py`가 실패합니다.

과제는 난이도(쉬움/보통/어려움 — 저작자의 사전 라벨이며, 점수 행렬이 실측으로

멀티턴 과제는 각 비교 대상이 **자기 자신의 이전 답변**을 이어받으므로, 턴을

고장난 것이고, 경계선 프롬프트를 전부 가장 보수적인 모델로 보내는 라우터는
오탐 거부에 돈을 내는 겁니다. `ambiguity-clarify`는 되묻는 답에 점수를 줍니다 —
v1 루브릭에서는 답 대신 질문하면 오히려 *감점*이라 스위트 전체가 자신감 있는
추측 쪽으로 기울어 있었습니다.

과제 정의는 `tasks/base/*.jsonl`·`tasks/k/*.jsonl`이고, 한·영 공용 원본
`tasks/_src/*.json`을 `tools/author_tasks.py`가 컴파일합니다. 장문 과제는 원문을
커밋하는 대신 결정적 생성기(`tools/generators.py`)가 작은 시드에서 만들어 냅니다.
에이전틱 과제는 각 스위트의 `fixtures/` 아래 시드 저장소와 함께 제공됩니다.

## 진화 과제 — 2026-09-07 에 35과제를 추가한 이유

점수 행렬(후보 모델 전부 × 과제 전부, 아래 *Oracle* 참조)은 과제마다 「후보
풀이 실제로 어떻게 했나」로 난이도 구간을 붙입니다. v12 스위트의 한국어 행렬은
**측정 과제의 15.5%만 `discriminative`(모델 따라 갈림) 또는 `frontier-only`**
(28/181)였고, 설계 관문 B2 는 40% 이상을 요구합니다. 더 문제는 코딩 블록이
**100% `cheap-sufficient`(가장 싼 모델도 통과)** 였다는 점입니다 — `code-write`
20·`code-debug` 11·`tool-use` 7 전부를 가장 싼 모델이 풀었으니, 이 과제들은
라우팅에 관해 아무 정보도 주지 못했습니다. 이런 벤치는 라우터를 순위 매길 수
없고 「무조건 가장 싼 모델」에게만 상을 줍니다.

더 어려운 과제를 손으로 쓰는 대신(저작자의 난이도 감이 틀린다는 걸 행렬이 계속
증명해 왔습니다) `tools/evolve_tasks.py` 가 *환경 진화*(Fan et al.,
arXiv:2609.04128, 2026-09)를 챗 모드 벤치 과제에 맞게 옮겼습니다. 씨앗 과제를
(상황, 기술) 단계의 연속으로 읽고, 세대마다 **한 방향**으로만 고칩니다 —
`length`(서로 얽힌 단계 추가)·`scenario`(같은 기술, 덜 흔한 상황)·`skill`(같은
상황, 더 드문 기술). 자손은 두 언어 모두에서 다음을 통과해야만 남습니다.

1. **정답** — 새 정답이 새 채점을 통과한다.
2. **오답** — 그럴듯한 오답과 빈 답은 실패한다.
3. **더 어려워짐** — *씨앗의* 정답이 새 채점에서 떨어진다. 즉 문장만 바꾼 게
   아니라 기준이 실제로 올라갔다.
4. **검토** — 생성 모델과 다른 회사의 검토자(Claude Opus 5 가 만들고 GPT-5.6
   Sol 이 검토)가 계획(전)과 과제(후)를 고정 기준으로 승인한다(숨은 조건 없음·
   정답 유일·한영 동일·현실적 요청·꼼수·상식퀴즈 금지).
5. **교차 확인** — 가장 싼 두 후보 모델이 한 번씩 풀어 본다. 둘 다 맞히면 아직
   변별이 안 되는 것이니 다음 세대로 한 번 더 진화한다(최대 3세대).

채택된 자손은 다른 과제와 똑같이 후보 8종 전체에 실측했습니다. 한국어 스위트
결과: **discriminative + frontier-only 28/181 (15.5%) → 46/216 (21.3%)**, 코딩
블록은 변별 과제 0 → 13. 아직 40% 관문엔 못 미치며, `tools/validate_suite.py` 가
이제 B2 를 행렬에서 실측해 충족될 때까지 위반으로 표시합니다.

숫자를 읽을 때 알아야 할 것:

- 언어당 35과제가 **추가**됐고 기존 218과제는 하나도 바뀌지 않았습니다
  (`tools/author_tasks.py --verify` 바이트 동일, v1 중첩분 동결 유지). id 는
  `-g<N>`(세대)으로 끝나고, 씨앗·방향·세대·싼 모델 프로브·「새 테스트가 씨앗과
  달리 무엇을 보는가」 메모까지 전체 계보가 `tasks/_src/evolved.json` 에 있습니다.
- 측정된 모든 과제의 실측 구간은 `tasks/_calibration/` 에 공개합니다(한국어는
  전체 행렬, 영어는 진화 과제분 — 영어 풀 행렬은 아직 없습니다).
- 아래 `v12` 기준 결과는 이 과제들이 생기기 **전** 218과제 스위트에서 돌린
  것입니다. 253과제 스위트의 회차는 공통 과제로만 `v12` 와 비교되며,
  `internal/compare_runs.py` 가 과제 집합이 다르면 자동으로 그렇게 합니다.
  전체 스위트의 새 기준선이 다음 예정 회차입니다.
- 진화는 off-policy 입니다. 파이프라인 어디서도 라우터를 읽지 않습니다. 이
  과제들 자체에 라우터를 맞추면 벤치가 무의미해지니, 과제 본문이 아니라
  `dev`/`test` 분할과 구간 분포를 쓰세요.

## 스위트 불변 조건

스위트 균형은 눈으로 보는 게 아니라 강제합니다. `tools/validate_suite.py`가 두
스위트를 `configs/suite_spec_v2.json`에 대조해 어긋나면 0이 아닌 코드로 끝납니다:
결정적 채점 70% 이상 · 어느 카테고리도 15% 초과 금지(코딩 블록은 35% 상한) ·
객관식 30% 상한·보기 3개 이상 · 입력 길이 대역 비율 선언 · Track A의 90% 이상
한/영 쌍 · 심사 평균과 객관 통과율은 절대 합산 금지 · 모든 품질 주장은 과잉
상향·과소 상향을 나란히 보고. 현재 스위트는 언어당 300과제 목표로 확장 중이라,
남은 구성 격차는 알려진 위반으로 출력됩니다.

## 공정성 원칙

- **정해진 승자가 없습니다.** 결과는 실행이 내놓는 그대로이며, 채점은
  결정적이고 심사 프롬프트는 블라인드입니다.
- **블라인드 심사.** 심사자는 어떤 비교 대상이 만든 응답인지 알 수 없고,
  자기 식별은 무시하도록 지시받습니다. **서로 다른 3사**의 심사 모델
  (기본: Claude Opus 5, GPT-5.6 Sol, Gemini 3.1 Pro)이 가중 루브릭으로
  1~10점을 독립 채점하고 평균이 최종 점수입니다. 리포트는 심사자×비교 대상
  평균을 전부 공개해 자사 편향을 검증할 수 있고, 심사자 간 합의도도 제공합니다.
- **같은 회선, 같은 프롬프트.** 모든 비교 대상이 동일 게이트웨이 엔드포인트에서
  동일 프롬프트·토큰 한도로 실행됩니다.
- **추론 깊이는 기본값.** `reasoning_effort`·`thinking`을 지정하지 않고 각 모델의
  기본값으로 실행합니다. 게이트웨이 기본 설정으로 실제 배달되는 가성비를 재는
  것이며(라우터가 모델을 호출하는 방식과 동일), 추론 깊이를 통일한 실험실
  비교는 아닙니다.
- **비용은 단일 출처.** 세션별 비용은 게이트웨이 서버측 계량(또는 응답의
  `usage.cost`)에서 오며, 자체 추정치는 쓰지 않습니다.
- **배달도 측정하되, 분리해서 보고합니다.** 호출은 재시도 없는 1회입니다.
  거부·빈 응답·생성 중 절단도 헤드라인 평균에 그대로 반영됩니다 — 실제
  호출자가 받은 결과이기 때문입니다. 동시에 전 건을 배달 실패 표에 공개하고,
  실패 제외 평균(`judge_mean_delivered`)을 병기해 안전 분류기 오탐이 모델
  품질로 위장하지 못하게 합니다.
- **양방향 라우팅 지표.** 아래 참조 — 단지 가장 싸다고, 단지 가장 좋다고
  보상받는 라우터는 없습니다.

## Oracle: 과잉 상향과 과소 상향

v1의 모든 지표는 *라우터 vs 고정 모델*이었습니다. v2는 *라우터 vs 통과했을
가장 싼 모델*을 더합니다.

1. **점수 행렬.** 에이전틱을 제외한 모든 과제를 라우터 후보 풀의 모든 모델에
   한 번씩 돌립니다(「풀 실행」: 모델 하나가 비교 대상 하나). 그 결과를
   `tools/build_score_matrix.py --from-run <풀 실행>`이 과제 → 모델 →
   {통과, 심사, 비용, 지연}으로 재구성합니다. 행렬은 캐시되고 풀이 바뀔 때만
   다시 만듭니다.
2. **과제별** oracle = 통과하는 풀 모델 중 가장 싼 것.
3. **실행별**로 `analyze --matrix`가 보고합니다:

| 지표 | 정의 | 벌하는 쪽 |
|---|---|---|
| **최적 선택 %** | 라우터가 정확히 oracle 모델을 골랐다 | 양방향 |
| **과잉 상향 %** | 라우터는 성공했지만 엄밀히 더 싼 모델도 성공했을 것 | 항상 프런티어 |
| **과소 상향 %** | 어떤 풀 모델은 통과하는데 라우터는 실패 | 항상 최저가 |
| **비용 후회 ×** | 라우터 비용 ÷ oracle 비용 | 항상 프런티어 |

행렬은 각 과제에 **실측 난이도 대역**도 붙입니다 — `cheap-sufficient`(가장 싼
모델이 통과), `discriminative`(어떤 모델은 통과·어떤 모델은 실패 — 라우팅이
돈을 벌어 오는 곳), `frontier-only`, `unsolved` — 그리고 리포트는 스위트의
몇 %가 discriminative인지 밝힙니다. 모든 모델이 통과하는 스위트는 라우터를
서열화할 수 없기 때문입니다. `tools/selftest_oracle.py`는 합성 행렬로 「항상
최저가」와 「항상 프런티어」 라우터가 둘 다 나쁜 점수를 받는다는 걸 증명합니다.

## 실행 방법

```bash
export SRB_API_KEY=...            # 게이트웨이 API 키

# 0. Track B 를 로컬에 생성 (포인터 -> 행, gitignore)
python3 tools/fetch_track_b.py
python3 tools/validate_suite.py   # 스위트 불변 조건 (구성 격차는 보고만, 치명 아님)

# 1. 챗 모드 응답 수집 (전 과제 × 전 비교 대상)
PYTHONPATH=src python3 -m smartroute_bench.runner --run-id r1 --skip-done

# 2. 객관 채점
PYTHONPATH=src python3 -m smartroute_bench.run_checks --run-id r1

# 3. 블라인드 심사 (3사 심사 패널, 루브릭 과제만)
PYTHONPATH=src python3 -m smartroute_bench.judge --run-id r1 --skip-done

# 4. 집계 + 리포트   (oracle 지표는 --matrix results/_matrix/<pool>.json 추가)
PYTHONPATH=src python3 -m smartroute_bench.analyze --run-id r1
PYTHONPATH=src python3 -m smartroute_bench.report --run-id r1 --lang ko   # -> report.html
```

위 명령은 영어 base 스위트를 실행합니다. 한국어 스위트는 각 단계(`runner`,
`run_checks`, `judge`, `analyze`)에 `--tasks tasks/k`를 붙이고 별도 `--run-id`를
쓰세요. 모든 단계가 `--skip-done`으로 재개 가능해서 네트워크가 끊겨도 두 번
지불하지 않고 이어집니다. 새 측정에 같은 `--run-id`를 재사용하지 마세요 —
결과는 실행별 추가 기록만 됩니다.

oracle 지표를 얻으려면 풀을 한 번 돌리고(`configs/arms.json`에 후보 모델마다
비교 대상 하나·전용 run-id), `tools/build_score_matrix.py`로 행렬을 만들어
`analyze --matrix`에 넘기세요. oracle은 풀에 상대적으로 정의됩니다 — 다른 풀로
만든 행렬은 다른 질문에 답하므로, 풀이 바뀌면 다시 만들어야 합니다.

**정기 재벤치**(라우터 변경마다)는 비교 대상 집합과 심사 패널을 실행 사이에
고정하고, 같은 스위트에서 새 실행을 직전 실행과 diff 하세요. 비교 대상이나
심사자가 바뀌면 헤드라인 심사 평균 대신 공통 심사자 부분집합만 비교하고, 변경
후 첫 실행을 새 기준선으로 삼으세요.

비교 대상·엔드포인트·심사자는 `configs/arms.json`에서 설정합니다.
OpenAI 호환(`/chat/completions`) 또는 Anthropic 호환(`/messages`)
게이트웨이면 무엇이든 동작하며, 라우팅 비교 대상은 `model`이 게이트웨이의
라우팅 가상 모델인 항목일 뿐입니다. 라우팅 결정은
`x-bizrouter-routed-model` 류의 응답 헤더가 있으면 그것으로 읽습니다.

에이전틱 과제는 워크스페이스에서 headless로 돌 수 있는 코딩 에이전트 CLI가
필요합니다. `adapters/agentic_bizcoder.py`가 [BizCoder](https://bizcoder.ai)
CLI 어댑터이고, 이 파일을 복사해 subprocess 호출만 바꾸면 다른 CLI로 교체할
수 있습니다.

서드파티 파이썬 의존성이 없습니다(표준 라이브러리만). 객관 채점은 PATH에 있는
툴체인(`node`, `go`, `rustc`, `sqlite3`)을 사용하고, 없으면 건너뜁니다.
`tools/make_run_manifest.py`는 실행 산출물의 SHA-256 매니페스트를 내보내,
검토자가 보낸 사람을 믿지 않고도 원시 시도 ↔ 분석 ↔ 근거의 정합을 확인할 수
있게 합니다.

## 출력물

`results/<run-id>/analysis.json`에 과제별·집계 수치가 담깁니다:
비교 대상별/카테고리별/난이도별/모드별 비용·품질·지연, 라우터의 모델 선택
분포, 심사자 간 합의도, 행렬을 넘긴 경우 oracle 지표, 라우팅된 답이 고정
모델보다 측정 가능하게 나빴던 과제 플래그(미스라우팅 후보). `report.html`은
같은 내용을 공유 가능한 페이지로 렌더링합니다.

## 측정 결과를 라우터로 되먹이기

한 번의 실행에서 나온 카테고리 점수는 *실측된* 능력 근거입니다. 능력 제안
페이로드로 내보낼 수 있습니다:

```bash
python3 tools/export_capability_evidence.py --run-id r1 --measured-at 2026-08-27 \
    > results/r1/capability_evidence.json
```

귀속 가능한 측정만 내보냅니다: 고정 비교 대상은 자기 모델을 직접 측정하고,
라우팅 비교 대상의 점수는 라우팅이 특정 모델에 사실상 집중(95% 이상)됐을 때만
그 모델의 실측으로 귀속됩니다. BizRouter는 이 파일을 **pending 능력 제안**
으로 인제스트해 관리자가 검토·승인해야만 실제 라우팅에 반영되며, 다른
게이트웨이도 같은 JSON을 소비할 수 있습니다.
